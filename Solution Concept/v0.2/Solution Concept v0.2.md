# 3. Концепция целевого решения
## 3.1 Краткое описание решения

**Пользователи:** 
- диспетчеры
- ответственные мастера
- исполнители
- представители клиентов
- руководитель сервисного направления

**Ценность:** Сейчас заявки ведутся в ручном режиме, диспетчеры не справляются с нагрузкой, исполнители не видят всех своих работ и их приоритетов, данные по заявкам теряются, часть заявок не исполняется вовремя, а клиенты не видят истории обращений.

С введением централизованной системы:
- диспетчеры и представители клиентов смогут создавать заявки в упрощённом режиме
- ответственные мастера смогут распределять работы между исполнителями и контролировать статусы заявок
- исполнители смогут видеть список выездных работ и приоритеты по ним
- руководитель сервисного направления сможет отслеживать проблемные заявки и выявлять причины задержек
- представители клиентов получат доступ к полной истории своих обращений

**Ключевые возможности:** 
- создание заявок
- назначение исполнителей на работы внутри системы
- отслеживание всей истории изменений по заявке
- прикрепление файлов к заявке
- переписка внутри системы
- получение уведомлений по просроченным заявкам

**Каналы:** 
- Веб-приложение для сотрудников МастерЛайн
- Веб-приложение для клиентов
- Мобильная версия сайта
- iOS-приложение
- Android-приложение
- Интеграция с почтой
- Телефония

**Границы:** 

| Возможность | Предложение для обсуждения |
| --- | --- |
| Вход в систему через корпоративную учетную систему | R1 |
| Вход в систему по логину и паролю | R1 |
| Регистрация обращения диспетчером | R1 |
| Назначение ответственного и исполнителей | R1 |
| Работа исполнителя с телефона | R1; способ реализации отдельно согласовать |

| История и важные уведомления | R1 |

| Самостоятельный кабинет клиента | Следующий релиз |
| Регистрация по ссылке приглашению | Следующий релиз |
| Клиентский чат-бот | Следующий релиз, согласовать приоритет и сроки |
| Телефония | Ручная регистрация обращения после звонка; интеграция отдельно |

На встрече было подтверждено ([Ссылка на Протокол](<Protokol.md>) ), что самостоятельный кабинет клиента является необходимым в рамках проекта, но не является обязательным для запуска. На первом этапе (R1) за регистрацию обращений отвечает только диспетчер: собирает заявки из почты в ручном режиме, регистрирует из телефонных звонков. 

Заказчик подтвердил, что для работы исполнителей нужны мобильный сайт и приложения для iOS и Android. Необходимо определить приоритеты и сроки реализации, какие способы работы исполнителей предполагаются на первом шаге (R1).

В ходе обсуждения была выявлена роль "Ответственный мастер", отвечающая за назначение исполнителей по работам в рамках заявки. Необходимо определить, какие функции она выполняет в ходе исполнения заявки, какими правами в отношении заявки обладает и нужны ли ей уведомления.

## 4.1 Функциональные требования

### Основные сценарии R1

| | |
| :--- | :--- |
| **Заголовок** | Просмотр всех заявок |
| **Участники** | Пользователь, FSM, Сервер |
| **Предусловие** | 1. Пользователь авторизован в системе. |
| **Триггер** | Пользователь выбрал пункт меню "Все заявки" в панели управления. |

### 4.2.7 Требования к логированию

- Неверный синтаксис запроса (400)
- Ресурс не найден (404)
- Слишком много запросов (429)
- Ошибки сервера (500, 503, 504)

### 4.2.8 Требования к аудиту

- Ошибки аутентификации (401)
- Ошибки авторизации (403)
- Создание заявки
- Изменение данных по заявке: номер, заголовок, клиент, дата регистрации, статус, приоритет, ответственный, крайний срок закрытия, фактическая дата закрытия, работы
- Удаление заявки
- Создание задачи
- Изменение данных задачи: заголовок, клиент, исполнитель, статус, крайний срок закрытия, фактическая даат закрытия
- Удаление задачи
- Добавление файлов к заявке иил задаче
- Удаление файлов из заявки или задачи

### 4.2.10 Требования переходного периода

- настройка интеграции с CRM
- настройка справочников
- настройка прав доступа по ролевой модели (руководитель сревисного направления, диспетчер, ответственный мастер, исполнители, представители клиентов)
- обучение пользователей
- частичнй перевод 1-2 команд и диспетчеров на FSM, все новые заявки создаются в FSM, старые закрываются в прошлой системе

- перевод всех пользователей в новую систему (уточнить необходимость миграции незакрытых и старых заявок)
